## User Constraints (from CONTEXT.md)

### Locked Decisions

### S3 publication strategy
- **D-01:** Publish S3 payloads with obstore direct create-if-absent at one deterministic immutable generation locator. Collision and ambiguous-response handling must inspect only that exact locator and its bound evidence; listings and timing never establish success.
- **D-02:** Keep an explicit configurable S3 upload-size bound and initially preserve the current 128 MiB default unless planning proves an obstore API constraint requires a different bound. Oversized payloads fail clearly. Do not introduce multipart temporary objects, conditional-copy publication, abandoned-upload cleanup debt, or a retained custom multipart fallback.
- **D-03:** Preserve the current signed-manifest SHA-256 plus byte-size canonical integrity contract during this phase. ETags are opaque transport evidence, not canonical content hashes. Phase 8 must benchmark SHA-256 against XXH3; a future digest change is deferred to SEED-003.

### Dependency packaging and S3 parity
- **D-04:** Make obstore a core dependency and use it for every built-in payload participant: filesystem, memory, and S3. S3 remains an explicitly configured topology. — **Reversibility:** costly — undoing this would restore multiple payload implementations and require another dependency and backend cutover.
- **D-05:** The first implementation gate must inventory and prove every S3 capability Cacheness actually consumes, including create-if-absent behavior, exact-object metadata lookup, ETag retrieval, optional version evidence, bounded reads, deletion, listing used for maintenance evidence, and error classification. If a required capability is absent, stop before production edits and replan; do not quietly retain boto3 or weaken the contract.
- **D-06:** After the parity gate passes, remove boto3 production payload mechanics. Test-only tooling may retain a dependency when genuinely required to provide deterministic mocked-S3 infrastructure, but it must not become a runtime fallback.

### Cutover semantics
- **D-07:** Perform one atomic implementation cutover after parity contracts pass. Do not add an obstore/legacy runtime selector, dual-write/read behavior, or a narrow boto3 escape hatch. — **Reversibility:** costly — restoring the prior mechanics would recreate parallel backend behavior and its separate recovery contract.
- **D-08:** Preserve current canonical generation-locator and signed-manifest contracts where straightforward. Unsupported development-era stores fail explicitly rather than receiving automatic compatibility reads. Keep explicit format/schema versions and offline migration/rebuild machinery for future releases.

### Handler and lifecycle boundaries
- **D-09:** Preserve `CacheHandler.put(data, Path, config)` and `get(Path, metadata)`, built-in native formats, and `store.handlers.register_handler(...)`. Handlers never receive obstore objects or managed locators. Retain private suffix-preserving staging/snapshots, descriptor validation, regular-file enforcement, and path containment around handler calls.
- **D-10:** Obstore supplies payload atomicity only. It must not become a visibility authority, lifecycle coordinator, metadata authority, cleanup journal, or source of catalog completeness. `BlobStore` continues to sequence prepare, publish, verify, promote, and exact cleanup under ADR 0001.

### Persisted transport evidence
- **D-11:** Persist S3 ETag, object size, and optional object version as signed, generation-bound, noncanonical transport evidence during the existing verification transition after publication and before promotion. This must use the existing lifecycle states rather than a second metadata update or a new coordination mechanism. — **Reversibility:** costly — it changes authority records and schemas across memory, SQLite, and PostgreSQL implementations.
- **D-12:** Expose a narrow developer-facing check that resolves the authoritative generation and compares its persisted transport evidence with an exact obstore `head()` result. This permits cheap remote identity validation without payload download. It must identify the generation checked and must not claim cryptographic payload verification or replace SHA-256 verification before deserialization.

### Acceptance boundary
- **D-13:** Phase 07.1 must deterministically qualify built-in handlers and a custom MCAP-style path handler across obstore LocalStore, MemoryStore, and mocked S3. Cover native suffix preservation, containment, single-regular-file enforcement, round trips, create-if-absent collision behavior, exact lost-response recovery, exact immutable-generation deletion, ETag evidence, upload-bound rejection, and streaming read snapshots.
- **D-14:** Phase 07.1 must demonstrate that the custom filesystem, memory, and S3 payload mechanics and boto3 runtime path are gone, while the payload-participant composition seam remains usable and no new lifecycle authority, journal, lease, queue, lock hierarchy, or cleanup source of truth was introduced.
- **D-15:** Phase 8 owns real AWS qualification, supported-platform and packaging matrices, measured RSS/performance budgets, and SHA-256-versus-XXH3 benchmarks. Phase 07.1 proves structural bounds and deterministic behavior without duplicating those release gates.

## Summary

Phase 07.1 cannot proceed to production planning under D-05 because obstore 0.11.1 does not provide a valid, documented way to apply Cacheness's required `ExpectedBucketOwner` binding to every S3 operation. The existing Phase 5 contract marks the exact capability `"Region plus ExpectedBucketOwner"` as `INTEGRATE`, because it binds requests to the intended AWS account. [VERIFIED: `.planning/phases/05-payload-backends-and-supported-topology-qualification/05-COVERAGE.md:9-15`] The current participant stores `expected_bucket_owner` and adds `ExpectedBucketOwner` to request kwargs. [VERIFIED: `src/cacheness/storage/backends/s3_backend.py:164-204,272-281`]

The official obstore 0.11.1 S3 configuration surface has no `expected_bucket_owner` key; the pinned runtime raises `obstore.exceptions.UnknownConfigurationKeyError` for that key. [CITED: https://developmentseed.org/obstore/latest/api/store/aws/] A generic `client_options.default_headers` workaround is not valid for the required bounded listing path: a pinned 0.11.1 runtime probe showed `list()` sends `x-amz-expected-bucket-owner` but omits it from the request's SigV4 `SignedHeaders`. AWS requires every included `x-amz-*` header to be part of the canonical request/signature. [CITED: https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv-create-signed-request.html] The tagged dependency source explains the gap: ordinary S3 requests and GET/HEAD explicitly add default headers before signing, while the list request constructs and signs its request without that step. [CITED: https://github.com/apache/arrow-rs-object-store/blob/v0.14.1/src/aws/client.rs]

All other required Cacheness S3 payload mechanics are present in obstore 0.11.1, and the post-unblock design is straightforward: keep `PayloadGenerationIOProvider` and `AuthorityLifecycleEngine`; compose one Cacheness-owned obstore generation-I/O adapter with `GuardedHandlerIO`; use `put(..., mode="create", use_multipart=False)` behind a 128 MiB cap; stream reads into private suffix-preserving snapshots; treat SHA-256 plus size as canonical; and carry separately signed transport evidence through the existing verification mutation into the promoted entry. [CITED: https://developmentseed.org/obstore/latest/api/put/] [VERIFIED: `.codex/skills/spike-findings-cacheness/references/handler-integration.md:12-61`] This design is recorded below so planning can resume without repeating research after the owner-binding blocker is resolved.

**Primary recommendation:** Stop before any production edit or dependency change. Resume planning only after an obstore version/fork demonstrates correctly signed `ExpectedBucketOwner` on put, head/get, delete, and list, or after an explicit user-approved revision removes the Phase 5 owner-binding requirement. Do not retain boto3 as a fallback.

### Blocking Evidence and Why the Generic Header Escape Hatch Fails

The source-of-truth Phase 5 row is verbatim: `| Amazon S3 / boto3 | Region plus ExpectedBucketOwner | INTEGRATE | Binds configured requests to the intended AWS account and region. |`. [VERIFIED: `.planning/phases/05-payload-backends-and-supported-topology-qualification/05-COVERAGE.md:10-15`]

At tag `py-v0.11.1`, obstore constructs `S3Store` from the upstream `AmazonS3ConfigKey` set and deliberately turns invalid keys into `UnknownConfigurationKeyError`; `expected_bucket_owner` is not in the exported documented/configured key set. [CITED: https://github.com/developmentseed/obstore/blob/py-v0.11.1/pyo3-object_store/src/aws/store.rs] The exact pinned runtime result was `UnknownConfigurationKeyError: Configuration key: 'expected_bucket_owner' is not valid for store 'S3'.` [VERIFIED: isolated obstore 0.11.1 runtime probe, 2026-09-12]

Obstore does expose arbitrary `client_options.default_headers`. [CITED: https://github.com/developmentseed/obstore/blob/py-v0.11.1/pyo3-object_store/src/client.rs] Its pinned `object_store` dependency is version `0.14.1`. [VERIFIED: official obstore tag `py-v0.11.1`, `Cargo.lock`:1423-1426] However, a local HTTP capture of `S3Store.list()` configured with `x-amz-expected-bucket-owner: 123456789012` produced an Authorization header whose `SignedHeaders` were exactly `host;x-amz-content-sha256;x-amz-date`; the owner header was transmitted but unsigned. [VERIFIED: isolated obstore 0.11.1 runtime probe, 2026-09-12] AWS states that any `x-amz-*` header included in a request must be added to `CanonicalHeaders`, and that any `x-amz-*` header must be included in the signature. [CITED: https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv-create-signed-request.html]

This is not a request to add a Cacheness signer or special HTTP client. Such a workaround would hand-roll AWS request semantics, widen the payload seam, and still need non-substitutable real-AWS proof. It also violates the phase's goal of replacing custom S3 mechanics with obstore. The permitted resolution is upstream capability (release or reviewed fork), or an explicit decision revising the locked owner-binding contract.

## Current Code Findings

### Existing Payload Seam and Engine

The topology vocabulary is exactly `PAYLOAD = "payload"`, `AUTHORITY = "authority"`, and `PROJECTION = "projection"`. [VERIFIED: `src/cacheness/storage/composition.py:202-207`] The payload protocol is already narrow:

```python
def materialize_handler_io(self) -> object:
    """Return the participant-rooted guarded generation-I/O primitive."""
    ...
```

[VERIFIED: `src/cacheness/storage/composition.py:238-249`]

`BlobStore._materialize_authority_store()` checks for exactly the lifecycle-facing methods `stage`, `publish_generation`, `open_snapshot`, `delete_or_prove_absent`, and `close`. [VERIFIED: `src/cacheness/storage/blob_store.py:773-807`] Retain the provider seam; replace what built-in providers materialize.

`AuthorityLifecycleEngine.put()` already performs the required sequence: stage; SHA-256 the retained descriptor; create and sign the canonical manifest; `prepare_mutation`; `publish_generation`; independently open and hash a private snapshot; `record_verification`; `promote_mutation`; then settle prior-generation cleanup debt. [VERIFIED: `src/cacheness/storage/lifecycle.py:392-550`] Replay also evaluates only the exact prepared locator and verifies exact SHA-256 plus size before promoting. [VERIFIED: `src/cacheness/storage/lifecycle.py:255-354`] Do not move any of these decisions into the obstore adapter.

The generation locator remains `generations/<storage-id>/<generation><suffix>`. [VERIFIED: `src/cacheness/storage/lifecycle.py:162-167`] Preserve it; do not add an obstore scheme or backend-specific path to the manifest.

### Guarded Handler Boundary

The handler staging suffix grammar is exactly `(?:\.[A-Za-z0-9_-]+){0,4}\Z` with a maximum length of `96`. [VERIFIED: `src/cacheness/storage/guarded_handler_io.py:32-33`] `GuardedStagedArtifact.open()` reopens the retained, validated artifact identity and yields its stream plus size. [VERIFIED: `src/cacheness/storage/guarded_handler_io.py:95-130`] The phase must keep this object and pass its opened descriptor, not its path, to obstore publication. [VERIFIED: `.codex/skills/spike-findings-cacheness/references/handler-integration.md:14-25,45-53`]

The current `GuardedHandlerIO` mixes retained security responsibilities with filesystem participant mechanics: `publish_generation()` calls `ManagedFileOps.create_stream_durable_exclusive`, `delete_or_prove_absent()` operates the managed root, and `open_snapshot()` copies a managed file. [VERIFIED: `src/cacheness/storage/guarded_handler_io.py:133-202,411-442`] After unblock, split or delegate those three mechanics to the obstore adapter while preserving private stage/snapshot creation, file mode, descriptor/inode validation, regular-file checks, and suffix checks.

### Mechanics to Remove After the Gate Passes

`BlobBackend` is a wide byte-CRUD abstraction with `write_blob`, `read_blob`, `delete_blob`, `exists`, default whole-buffer streaming helpers, and `get_size`. [VERIFIED: `src/cacheness/storage/backends/blob_backends.py:28-159`] The memory participant owns a separate `_storage: Dict[str, bytes]` plus `InMemoryHandlerIO`, which reads a staged descriptor into memory and writes full payload bytes to a private snapshot. [VERIFIED: `src/cacheness/storage/backends/blob_backends.py:277-356,359-429`] These mechanics become obsolete when LocalStore and MemoryStore use the same adapter.

The S3 participant currently imports boto3/botocore, implements request construction, single and multipart publication, ambiguous-response classification, streamed snapshot download, exact delete/head, bounded object inventory, and multipart-upload inventory. [VERIFIED: `src/cacheness/storage/backends/s3_backend.py:1-49,147-230,455-632,657-922`] D-02 requires removal of multipart creation/upload/completion/abort/inventory and their configuration (`multipart_threshold`, `part_size`, `max_multipart_parts`, `max_upload_attempts`). D-06 requires removal of production boto3 imports and `BOTO3_AVAILABLE` exports after parity passes.

### Migration and Rebuild Coupling

The offline migration code currently selects destination behavior by introspection: it calls an S3-only `migration_candidate_locator`/`write_migration_candidate` when present, otherwise calls the wide backend's `write_blob`, and special-cases a `memory://` returned locator. [VERIFIED: `src/cacheness/storage/migration.py:2016-2027,3384-3450`] That is the largest hidden consumer of the old backend mechanics. After unblock, migration must publish exact candidate locators through a backend-neutral method on the same generation-I/O adapter and must stop inspecting backend classes/schemes.

For same-format copy, stream/copy the already verified private `source_snapshot.path` through a descriptor-preserving adapter method instead of `read_bytes()` plus backend byte CRUD. For transformed payloads, keep the existing handler transformation and route its validated output through the same participant method. These recommendations preserve the current stopped-worker authority and do not add another maintenance authority. [VERIFIED: `src/cacheness/storage/migration.py:3357-3469`] [VERIFIED: `docs/adr/0001-topology-specific-storage-guarantees.md:139-170`]

This flow preserves the ADR's exact transaction boundary: memory/SQLite/PostgreSQL authority changes are atomic only within the authority; object effects are external immutable effects made crash-consistent by durable intent, exact verification, replay, and cleanup debt. [ASSUMED] Keep `FilesystemBlobBackend`, `InMemoryBlobBackend`, and `S3BlobBackend` only as thin topology participant constructors if their names remain useful; each should materialize the same adapter around its store. [ASSUMED]

### Locator and Handler Rules

Validate locators in Cacheness before every obstore call. The accepted namespace should be the existing engine's `generations/...` for normal operations and the existing explicit migration-candidate namespace for stopped-worker maintenance. Reject absolute paths, schemes, backslashes, empty/dot components, traversal, alternate prefixes, and unexpected characters. [VERIFIED: `.codex/skills/spike-findings-cacheness/references/backend-mechanics.md:16-18`] This pre-validation is essential because a pinned LocalStore probe accepted the input `/absolute` as a store-relative object name even though Cacheness requires absolute-path rejection. [VERIFIED: isolated obstore 0.11.1 LocalStore probe, 2026-09-12]

Keep the exact public handler calls `CacheHandler.put(data, Path, config)` and `CacheHandler.get(Path, metadata)`. The handler receives only private temporary paths and never a LocalStore root path, memory-store object, S3 key, or obstore instance. [VERIFIED: `.codex/skills/spike-findings-cacheness/references/handler-integration.md:3-10,45-53`]

Pass the retained open staged file object to `store.put`; do not pass the validated path and reopen it inside obstore. The current retained-descriptor mechanism exists specifically to prevent a between-validation-and-publication path race. [VERIFIED: `src/cacheness/storage/guarded_handler_io.py:52-121`] [VERIFIED: `.codex/skills/spike-findings-cacheness/references/handler-integration.md:18-25,50-51`]

### Publication and Ambiguous Response Pattern

The implementation call is:

```python
result = store.put(
    locator,
    source,
    mode="create",
    use_multipart=False,
)
```

[CITED: https://developmentseed.org/obstore/latest/api/put/]

Check the descriptor's byte size against `max_upload_bytes` before invoking `put`. Preserve the current initial default exactly as `_DEFAULT_DOWNLOAD_LIMIT = 128 * 1024 * 1024` and current constructor defaults `max_upload_bytes: int = _DEFAULT_DOWNLOAD_LIMIT` and `max_download_bytes: int = _DEFAULT_DOWNLOAD_LIMIT` unless the plan deliberately renames the constant. [VERIFIED: `src/cacheness/storage/backends/s3_backend.py:46-49,164-183`] Obstore documents that non-multipart put materializes the full input in memory; that is why the cap is a correctness/resource boundary rather than a performance claim. [CITED: https://developmentseed.org/obstore/latest/api/put/]

Normalize only `AlreadyExistsError`/known precondition collision into the existing immutable-generation collision outcome. For a success, collision, or plausibly ambiguous transport response, inspect only the exact locator, stream it to a private snapshot, and compare canonical SHA-256 plus byte size to the already prepared manifest. Matching bytes make publication idempotently complete; absence remains incomplete; mismatch is conflict. [VERIFIED: `.codex/skills/spike-findings-cacheness/references/lifecycle-and-recovery.md:16-36`] Do not use list results or elapsed time.

The adapter should expose an injected object-store-like seam for deterministic fault tests. A test wrapper can call through to the real MemoryStore or moto-server S3Store, then raise once to model a lost response; production configuration still must not expose a boto3 client or runtime fallback. [ASSUMED]

### Snapshot and Delete Pattern

For reads, call exact `get(locator)`, validate the returned `GetResult.meta`, and consume `GetResult.stream(min_chunk_size=...)` into a mode-`0600`, private, suffix-preserving file. Count chunks and bytes; reject a response whose bytes exceed the configured limit or whose final byte count differs from `ObjectMeta.size`; flush and fsync before yielding `GuardedReadSnapshot`. [CITED: https://developmentseed.org/obstore/latest/api/get/] [VERIFIED: `.codex/skills/spike-findings-cacheness/references/handler-integration.md:27-35`] The lifecycle engine must still calculate canonical SHA-256 plus size before handler deserialization. [VERIFIED: `src/cacheness/storage/lifecycle.py:501-520,778-848`]

MemoryStore may return the entire object in one chunk, so `min_chunk_size` is not a maximum-memory guarantee. [VERIFIED: `.codex/skills/spike-findings-cacheness/references/backend-mechanics.md:50-53`] Structural size/work caps remain testable here; RSS budgets belong to Phase 8 under D-15.

Delete exactly the never-reused immutable locator, normalize only known absence, then call exact `head(locator)`. Only `NotFoundError`/known `FileNotFoundError` proves absence; any other error remains typed backend/configuration/permission failure, and a still-present object remains cleanup debt. [CITED: https://developmentseed.org/obstore/latest/api/delete/] [CITED: https://developmentseed.org/obstore/latest/api/exceptions/] [VERIFIED: `.codex/skills/spike-findings-cacheness/references/backend-mechanics.md:19-21,50-51`]

### Error Normalization

Map obstore exceptions at the Cacheness adapter boundary, preserving `raise ... from error` and operation/stage context. [VERIFIED: `AGENTS.md` Error Handling directives]

| obstore/built-in error | Cacheness meaning | Rule |
|---|---|---|
| `AlreadyExistsError`, create precondition | immutable generation collision | The engine verifies the exact locator; never overwrite. [CITED: https://developmentseed.org/obstore/latest/api/exceptions/] |
| `NotFoundError`, operation-documented `FileNotFoundError` | absence only for the exact validated locator | Do not treat arbitrary `GenericError` as absence. [CITED: https://developmentseed.org/obstore/latest/api/exceptions/] |
| `InvalidPathError`, `ValueError` from locator parsing | unsafe/invalid participant input | Cacheness validation should normally reject before the call. |
| `PermissionDeniedError`, `UnauthenticatedError` | backend authentication/authorization failure | Never convert to miss or absence. |
| `PreconditionError` | inspect operation context | Create may be collision; read/head precondition is not absence. |
| `UnknownConfigurationKeyError`, `NotSupportedError` | construction/capability failure | Fail at topology construction/initialization. |
| `GenericError`, `JoinError`, transport-raised failures | typed backend failure; publication may be ambiguous | Exact digest+size classification is permitted only when the operation may have committed. |

### Anti-Patterns to Avoid

- **Generic default-header owner workaround:** It leaves list's owner header unsigned in 0.11.1 and is therefore the current blocker. [VERIFIED: pinned runtime probe, 2026-09-12]
- **Multipart temp/copy publication:** D-02 rejects its hidden objects, upload sessions, and cleanup obligations.
- **Boto3 runtime fallback:** D-05/D-07 forbid a parity escape hatch or runtime selector.
- **Obstore listing as catalog:** Authority promotion, not object presence, defines visibility. [VERIFIED: `docs/adr/0001-topology-specific-storage-guarantees.md:88-97`]
- **Handlers over obstore objects/streams:** D-09 keeps the path contract and private snapshot lifetime.
- **Raw ETag as digest:** ETag and version are opaque transport evidence; canonical SHA-256 plus size remains required.
- **A second evidence update after promotion:** D-11 requires the existing verification mutation and atomic authority promotion.
- **Adding locks, queues, leases, journals, or sidecars:** ADR stop conditions require replanning instead. [VERIFIED: `docs/adr/0001-topology-specific-storage-guarantees.md:172-192`]

## Common Pitfalls

### Pitfall 1: Treating a Generic Header as an AWS Owner-Binding Feature

**What goes wrong:** the request appears to carry `x-amz-expected-bucket-owner`, yet the list request does not include it in SigV4 `SignedHeaders`; this does not satisfy the locked account-binding contract. [VERIFIED: pinned obstore 0.11.1 capture probe, 2026-09-12]

**Why it happens:** `client_options.default_headers` is generic HTTP configuration, not an S3 semantic configuration key; obstore 0.11.1 rejects `expected_bucket_owner` as unknown. [VERIFIED: pinned obstore runtime probe, 2026-09-12]

**How to avoid:** require an explicit, correctly signed owner option demonstrated for create/head/get/delete/list before any production edit. **Warning sign:** parity evidence cites only PUT/GET or checks header presence without inspecting the SigV4 signed-header set.

### Pitfall 2: Accidentally Replacing the Lifecycle Authority

**What goes wrong:** `head()` or list presence becomes visibility, repair, or delete authority. That permits an unpromoted object to escape or an eventually consistent inventory observation to revoke a committed generation. [VERIFIED: `docs/adr/0001-topology-specific-storage-guarantees.md:88-97`]

**How to avoid:** exact object calls produce evidence; only the authoritative entry snapshot decides what users can see and what reconciliation may delete. **Warning sign:** a normal `get()` succeeds from an object key when `authority.read_entry(key)` is absent.

### Pitfall 3: Losing Path-Based Handler Isolation

**What goes wrong:** a handler receives an obstore object or a remote locator, or its relative sidecar files escape the private snapshot/staging directory. [VERIFIED: `src/cacheness/storage/guarded_handler_io.py:171-279`]

**How to avoid:** materialize a complete bounded private local snapshot, apply suffix and containment checks, reject non-regular files/symlink escapes, call the unchanged handler, and clean the private directory deterministically. **Warning sign:** a handler signature or custom MCAP-style fixture changes.

### Pitfall 4: Assuming Delete Reports Absence Uniformly

**What goes wrong:** backend-specific delete behavior is used as proof the exact generation is gone. [CITED: https://developmentseed.org/obstore/latest/api/store/#obstore.store.delete]

**How to avoid:** make exact delete idempotent and classify the result through exact post-delete `head`; never list to prove one locator is absent. **Warning sign:** `delete()` return value alone drives cleanup-debt resolution.

### Pitfall 5: Materializing Beyond the Upload Bound

**What goes wrong:** nonmultipart `put` buffers the whole source after a large handler result has already consumed disk/time; a too-late size check loses the intended bounded failure. [CITED: https://developmentseed.org/obstore/latest/api/store/#obstore.store.put]

**How to avoid:** check staged regular-file size before opening/uploading, enforce the configured cap (initially 128 MiB), and use `use_multipart=False`. **Warning sign:** `put()` begins before the checked size/cap decision or any multipart option becomes true.

### Pitfall 6: Comparing ETags as Though They Were SHA-256

**What goes wrong:** quoted/unquoted formatting, multipart behavior, encryption, proxies, or versioning semantics turn an opaque ETag into a false integrity claim. [ASSUMED]

**How to avoid:** normalize only representation-level quoting if official behavior requires it, persist exactly what was observed, compare opaque values only within the same store contract, and retain SHA-256 plus size as the verification gate. **Warning sign:** a read skips digesting because ETags match.

### Pitfall 7: Forgetting Schema Coupling

**What goes wrong:** one authority backend silently drops evidence or a schema bump makes current signed manifests claim stale version dimensions. [VERIFIED: `src/cacheness/storage/manifest.py:73-75,120-160`]

**How to avoid:** update memory, SQLite, PostgreSQL, migration snapshots, serializers, reopen tests, and version fixtures as one wave. **Warning sign:** only `EntrySnapshot` changed and database round-trip tests still use default-empty evidence.
