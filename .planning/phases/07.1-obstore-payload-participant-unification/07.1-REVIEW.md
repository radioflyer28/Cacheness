## Summary

The obstore cutover preserves the intended single-authority architecture and the fixed Phase 07.1 quick/all verifier passes. Adversarial review nevertheless found one fail-open integrity boundary: persisted transport-evidence bytes can be modified into a noncanonical representation without invalidating their HMAC. Three additional quality defects leave that boundary untested, publish obsolete migration schema constants, and give users a handler example that the new guarded staging code rejects.

The repository-wide bare pytest command was also attempted. It stops during collection because pandas is absent from the current base environment; that optional-environment qualification is explicitly deferred to Phase 8 and is not reported as a Phase 07.1 finding.

## Critical Issues

### CR-01: Noncanonical evidence bytes pass signature verification

**Classification:** BLOCKER

**File:** `src/cacheness/storage/transport_evidence.py:264-301`

**Issue:** `from_canonical_bytes()` parses JSON and reconstructs the dataclass, but never proves that the supplied bytes equal the canonical encoding. `verify()` then computes the HMAC over newly canonicalized fields rather than the persisted bytes. Consequently, an attacker or corrupt authority row can prepend whitespace, change key order, or use alternate JSON escaping and the evidence still verifies. This contradicts the method's canonical-byte contract, the phase's strict fail-closed parser requirement, and the manifest boundary's existing byte-for-byte canonicality rule. It was reproduced with `altered = b" " + evidence.canonical_bytes()`: `from_canonical_bytes(altered).verify(...)` succeeds.

**Fix:** Reject any alternate representation before returning the decoded evidence:

```python
evidence = cls(...)
if not hmac.compare_digest(evidence.canonical_bytes(), raw):
    raise _evidence_error("Transport evidence is not canonical JSON")
return evidence
```

Add cases for leading/trailing whitespace, reordered fields, escaped Unicode, and alternate slash escaping. Keep this inside the existing evidence parser; it does not add lifecycle state or another authority.

## Warnings

### WR-01: The fixed security verifier does not run its parser-hardening tests

**Classification:** WARNING

**File:** `tools/verify_phase071_contracts.py:176-184`

**Issue:** Threat `T-07.1-05-02` is the plan's evidence-parser tampering threat, but the fixed verifier maps it only to `test_opaque_etag_is_preserved_without_digest_interpretation`. Neither `test_tampered_evidence_fails_closed` nor `test_malformed_or_unknown_evidence_is_rejected_before_verification` is present in the quick or all inventory. The verifier therefore reports complete security coverage while the parser defect in CR-01 remains green.

**Fix:** Map the parser threat to exact parser/tamper selectors and add a canonical-byte rejection selector. Keep the opaque-ETag test under the ETag/content-identity threat rather than using it as parser evidence.

### WR-02: Exported migration authority versions still identify retired schemas

**Classification:** WARNING

**File:** `src/cacheness/storage/migration_authority.py:24-26`

**Issue:** The phase advances SQLite authority schema 8 to 9 and PostgreSQL schema/capability 4 to 5, but this public module still exports `SQLITE_MIGRATION_AUTHORITY_SCHEMA_VERSION = 8`, `POSTGRESQL_MIGRATION_AUTHORITY_SCHEMA_VERSION = 4`, and `postgresql-lifecycle-authority-v4` (via `__all__` at lines 471-475). Internal code currently ignores these constants, which makes the drift easy to miss, but an external maintenance consumer importing them receives identifiers that ordinary authority open now rejects.

**Fix:** Remove the unused duplicated constants or derive/re-export them from the canonical authority modules so the migration surface cannot drift independently. Do not add a compatibility reader for schema 8/4.

### WR-03: Store-local handler documentation returns an unsupported result field

**Classification:** WARNING

**File:** `README.md:745-759` (also `docs/PLUGIN_DEVELOPMENT.md:54-67`)

**Issue:** The newly recommended `store.handlers.register_handler(...)` example returns `file_path`, but `GuardedHandlerIO._staged_artifact()` accepts only `actual_path` (`src/cacheness/storage/guarded_handler_io.py:259-265`). Following the documented example therefore raises `CacheUnsafePathError` on the first `BlobStore.put()` instead of registering a working custom handler. The plugin guide repeats the same stale field and even tests `metadata["file_path"]`, so its example validates the obsolete contract rather than the shipped guarded participant seam.

**Fix:** Return `{"actual_path": str(output), "storage_format": ...}` in every BlobStore/store-local handler example and update the guide's round-trip assertion accordingly. Add one documentation example test that runs through `BlobStore.put/get`, not just direct handler calls.
