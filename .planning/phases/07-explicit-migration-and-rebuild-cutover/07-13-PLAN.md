<interfaces>
`BlobStore.put_entry()` currently returns `BlobReceipt(operation_id, key, generation, locator, expectation, catalog_revision, projections)` but accepts no caller-supplied operation identity. `AuthorityLifecycleEngine.put()` currently generates a fresh operation ID immediately before `LifecycleAuthority.prepare_mutation(MutationSpec)`; memory, SQLite, and PostgreSQL authorities already persist exact operation-keyed mutation records and make prepare/promotion replay-safe for the same exact spec. This plan adds one bounded read primitive for that existing record, not a second authority. Rebuild currently retains receipts only in a local list, stores one aggregate digest after all puts, passes an empty receipt tuple on verification failure, and has no rebuild-state branches in `resume()`.
</interfaces>

<planner_assumptions>
- MIGR-05 requires authenticated durable attribution for each completed destination batch and replay from every declared rebuild state; incidental destination keys never prove progress.
- MIGR-06 keeps rebuild separate from physical migration: reads use authenticated source handlers, writes use destination BlobStore lifecycle, and evidence never becomes destination authority.
- Destination cleanup is an external retryable effect. It must preserve exact conflicting/current entries and the complete source, not provide cross-resource rollback.
- The response-loss repair uses two existing durable boundaries in order: authenticated maintenance evidence records the deterministic intended rebuild operation before calling BlobStore; the single canonical destination authority records the exact `MutationSpec` before immutable payload publication and classifies retry. Neither record adopts a destination entry from key presence, listing, path, or timing.
</planner_assumptions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| authenticated rebuild intent -> canonical destination authority | A deterministic operation is recorded before BlobStore commit; only its exact authority mutation may satisfy response-loss retry. |
| authenticated rebuild receipts -> destination BlobStore | Replayed or forged receipts must not authorize completion or cleanup. |
| source handler -> destination lifecycle | Trusted application payloads cross handlers only after source authenticity/integrity checks. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-07-G13-01 | Tampering | Rebuild intents and receipt batches | high | mitigate | Authenticate a deterministic exact operation intent before each put, then bind the canonical BlobReceipt to run, plan, destination identity, ordinal, and bounded batch. |
| T-07-G13-02 | Spoofing | Cleanup ownership | high | mitigate | Compare exact key/generation/locator/expectation before delete; preserve mismatches as debt. |
| T-07-G13-03 | Repudiation | Verification failure | medium | mitigate | Record receipt-backed cleanup outcome and remaining debt before terminal evidence state. |
| T-07-G13-04 | Elevation of Privilege | Evidence-based adoption | high | mitigate | Resume recognizes only authenticated receipts or a pre-recorded operation ID resolved by the canonical authority; unrecorded keys never count as progress. |
| T-07-G13-05 | Information Disclosure | Rebuild evidence | medium | mitigate | Persist ownership identifiers/digests only and retain signing material behind the configured provider. |
</threat_model>
