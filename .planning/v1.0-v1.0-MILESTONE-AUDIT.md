# Cacheness v1.0 Milestone Audit

## Verdict

The milestone achieved its central architectural goal for the qualified local
scope: Cacheness now has one storage lifecycle owned by `BlobStore`, and
`UnifiedCache` is a policy layer that uses that engine rather than a second
payload lifecycle. The obstore cutover materially improved reliability by
replacing separate filesystem, memory, and S3 payload mechanics with one
guarded immutable-generation participant.

The milestone is not yet an adopter-ready public library release. The dominant
remaining blocker is productization, not storage correctness: the primary
documentation and many examples describe the pre-cutover API. A developer who
knows the current API can use the repository locally; a developer who follows
the README cannot.

Do not respond to this audit by adding locks, queues, compatibility shims,
parallel authorities, or more lifecycle coordination. Close the adoption and
evidence gaps around the architecture that is already working.

## Original Intent Assessment

| Goal | Result | Evidence |
| --- | --- | --- |
| Blob storage is independent of cache policy | Achieved | `BlobStore` owns entry publication, reads, deletion, clear, recovery, catalog metadata, and handler dispatch. |
| Cache uses the blob store as its engine | Achieved | `UnifiedCache` delegates payload-plus-authoritative-catalog operations to `BlobStore` while retaining keying, TTL, invalidation, eviction, and statistics. |
| One store need not serve cache and non-cache roles simultaneously | Achieved | Role separation is by composition; cache instances use a store engine without requiring a shared user-facing namespace. |
| Backend-neutral reliable payload mechanics | Achieved for declared tiers | Filesystem, memory, and S3 adapters use `ObstoreGenerationIO`; canonical authority still governs visibility and reconciliation. |
| Same-key contention cannot corrupt committed state | Achieved for qualified local topology | Current regression evidence covers success, conflict, and typed retryable outcomes without claiming universal scheduling guarantees. |
| Custom catalog metadata | Achieved with bounded scope | Direct stores can define, persist, query, update, and reopen typed catalog fields. |
| Custom serialization handlers | Achieved, poorly documented | Store-local registration and path-based custom handlers work for local and memory participants, including MCAP-style round trips. |
| Publicly usable library | Partial | Package/build gates pass locally, but primary onboarding documents and package identity are stale and no current immutable release exists. |

## What Obstore Did—and Did Not—Solve

Obstore removed a large source of duplicated risk. Built-in payload operations
now share one participant abstraction for immutable publication, exact reads,
listing, deletion, containment, and transport evidence. This reduced the amount
of custom filesystem/S3 mechanics Cacheness must maintain and aligned local,
memory, and mocked-S3 behavior.

Obstore did not make metadata and payload one distributed transaction. The
canonical metadata authority, immutable generations, typed conflicts, cleanup
debt, and deterministic reconciliation remain necessary. That is the bounded
model required by ADR 0001, not an unfinished attempt at cross-resource ACID.

## Requirement Reconciliation

The canonical requirement ledger contains 44 v1 requirements:

- 40 are satisfied by traceability, plan summaries, current verification, and
  cross-phase runtime evidence.
- `CACH-06` is partial. The implementation is coherent, but the requirement says
  the milestone *publishes* a coherent surface; the public documentation
  publishes several removed surfaces instead.
- `CACH-07` was reopened after this audit when the user approved direct removal
  of the separate `SqlCache` subsystem in Phase 10 before milestone completion.
- `BACK-05` is explicitly deferred and NOT_QUALIFIED. Mocks, emulators, and
  fail-closed runners are not real PostgreSQL/Amazon-S3 qualification.
- `QUAL-06` is explicitly deferred and NOT_QUALIFIED. macOS diagnostics are not
  the controlled-Linux benchmark record.
- No requirement is unmapped or orphaned.

The two deferred requirements were consciously removed from local-readiness
acceptance. They are external release claims, not hidden defects in the local
engine.

## End-to-End Integration

### Working flows

1. Minimal wheel import and guaranteed public exports.
2. Memory-backed `BlobStore` generic-object round trip.
3. Filesystem payload plus SQLite authority across close and reopen.
4. NumPy NPZ/Blosc handling through the local obstore participant.
5. Store-local custom MCAP-style handlers on local and memory stores.
6. Catalog metadata put, query, update, and reopen.
7. `UnifiedCache` put, lookup, TTL/invalidation, and exact deletion through
   `BlobStore`.
8. Clear, reconciliation, offline migration, and rebuild using canonical
   authority and exact immutable generations.

| BlobStore and handler extension guides | Constructors, metadata-backend descriptions, and global handler registration refer to the pre-cutover architecture. |

## Missing Productization Work

The smallest responsible closure phase is documentation and release-surface
work:

1. Rewrite or remove stale README, BlobStore, API-reference,
   configuration/backend-selection, security, and plugin-development material.
2. Publish two canonical quick starts: memory/local experimentation and durable
   filesystem-plus-SQLite use.
3. Make promoted examples executable contract tests and clearly archive
   historical examples.
4. Document a custom-handler conformance contract with an MCAP-style example,
   including payload identity, versioning, suffix, containment, staging, and
   migration responsibilities.
5. State the 128 MiB default transfer ceiling, bounded staging behavior,
   catalog-field limitations, and topology nonclaims prominently.
6. Make optional dataframe absence quiet until the feature is requested.
7. Update package description, version/release notes, and decide whether to
   publish a local-only prerelease before remote qualification.
8. Capture the missing Narwhals investigation as a future seed.
9. Refresh Phase 3 and Phase 8 validation frontmatter/reports without changing
   production lifecycle code.

## Explicitly Deferred or Future Work

The following should not be smuggled back into this milestone as reliability
fixes:

- Real PostgreSQL/Amazon-S3 qualification and immutable publication (`SEED-007`).
- Controlled-Linux performance distributions (`SEED-006`).
- Native Windows qualification (backlog Phase 999.1).
- Larger/streaming payload and multipart work (`SEED-002`/`SEED-004`).
- Reconsidering XXH3 for blob integrity (`SEED-003`); current canonical SHA-256
  semantics should not change incidentally.
- TensorFlow removal (`SEED-005`).
- General async, deduplication/reference counting, distributed invalidation,
  or new backend families (v2 scope).

## Recommended Exit

Complete Phase 9's adoption-surface closure, then Phase 10's direct removal of
the unrelated `SqlCache` subsystem. After both, rerun the bounded local gates
and complete the milestone. Neither phase should reopen the storage state
machine unless those checks demonstrate a concrete current failure.
