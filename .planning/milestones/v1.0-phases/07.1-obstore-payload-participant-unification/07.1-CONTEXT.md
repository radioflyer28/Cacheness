# Phase 07.1: Obstore Payload Participant Unification - Context

**Gathered:** 2026-09-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace Cacheness's custom filesystem, memory, and S3 payload mechanics with
obstore behind the existing payload-participant seam. `BlobStore` and its
lifecycle authority continue to own intent, committed visibility,
reconciliation, and cleanup debt. Obstore owns only payload byte/object
mechanics. Existing path-based format handlers and custom-handler registration
remain intact.

</domain>

<decisions>
## Implementation Decisions

### S3 publication strategy
- **D-01:** Publish S3 payloads with obstore direct create-if-absent at one deterministic immutable generation locator. Collision and ambiguous-response handling must inspect only that exact locator and its bound evidence; listings and timing never establish success.
- **D-02:** Keep an explicit configurable S3 upload-size bound and initially preserve the current 128 MiB default unless planning proves an obstore API constraint requires a different bound. Oversized payloads fail clearly. Do not introduce multipart temporary objects, conditional-copy publication, abandoned-upload cleanup debt, or a retained custom multipart fallback.
- **D-03:** Preserve the current signed-manifest SHA-256 plus byte-size canonical integrity contract during this phase. ETags are opaque transport evidence, not canonical content hashes. Phase 8 must benchmark SHA-256 against XXH3; a future digest change is deferred to SEED-003.

### Dependency packaging and S3 parity
- **D-04:** Make obstore a core dependency and use it for every built-in payload participant: filesystem, memory, and S3. S3 remains an explicitly configured topology. — **Reversibility:** costly — undoing this would restore multiple payload implementations and require another dependency and backend cutover.
- **D-05:** The first implementation gate must inventory and prove every S3 capability Cacheness actually consumes, including create-if-absent behavior, exact-object metadata lookup, ETag retrieval, optional version evidence, bounded reads, deletion, listing used for maintenance evidence, and error classification. If a required capability is absent, stop before production edits and replan; do not quietly retain boto3 or weaken the contract.
- **D-06:** After the parity gate passes, remove boto3 production payload mechanics. Test-only tooling may retain a dependency when genuinely required to provide deterministic mocked-S3 infrastructure, but it must not become a runtime fallback.
- **D-16:** Supersede Phase 5's `Region plus ExpectedBucketOwner` integration row for the obstore S3 cutover. Cacheness will not expose or emulate `ExpectedBucketOwner` because obstore 0.11.1 cannot sign it correctly across every consumed operation. Treat this as a documented defense-in-depth limitation, not a payload-integrity or lifecycle exception: require explicit bucket and region configuration, rely on AWS credentials/IAM and bucket policy for authorization, reject production custom endpoints, and preserve canonical SHA-256 verification plus signed ETag/size/version evidence. Do not introduce a fork, custom SigV4 layer, boto3 escape hatch, or parallel participant to recover this feature. — **Reversibility:** moderate — a future obstore release may restore owner pinning through the same participant without changing lifecycle authority.

### Cutover semantics
- **D-07:** Perform one atomic implementation cutover after parity contracts pass. Do not add an obstore/legacy runtime selector, dual-write/read behavior, or a narrow boto3 escape hatch. — **Reversibility:** costly — restoring the prior mechanics would recreate parallel backend behavior and its separate recovery contract.
- **D-08:** Preserve current canonical generation-locator and signed-manifest contracts where straightforward. Unsupported development-era stores fail explicitly rather than receiving automatic compatibility reads. Keep explicit format/schema versions and offline migration/rebuild machinery for future releases.

### Handler and lifecycle boundaries
- **D-09:** Preserve `CacheHandler.put(data, Path, config)` and `get(Path, metadata)`, built-in native formats, and `store.handlers.register_handler(...)`. Handlers never receive obstore objects or managed locators. Retain private suffix-preserving staging/snapshots, descriptor validation, regular-file enforcement, and path containment around handler calls.
- **D-10:** Obstore supplies payload atomicity only. It must not become a visibility authority, lifecycle coordinator, metadata authority, cleanup journal, or source of catalog completeness. `BlobStore` continues to sequence prepare, publish, verify, promote, and exact cleanup under ADR 0001.

### Persisted transport evidence
- **D-11:** Persist S3 ETag, object size, and optional object version as signed, generation-bound, noncanonical transport evidence during the existing verification transition after publication and before promotion. This must use the existing lifecycle states rather than a second metadata update or a new coordination mechanism. — **Reversibility:** costly — it changes authority records and schemas across memory, SQLite, and PostgreSQL implementations.
- **D-12:** Expose a narrow developer-facing check that resolves the authoritative generation and compares its persisted transport evidence with an exact obstore `head()` result. This permits cheap remote identity validation without payload download. It must identify the generation checked and must not claim cryptographic payload verification or replace SHA-256 verification before deserialization.

### Acceptance boundary
- **D-13:** Phase 07.1 must deterministically qualify built-in handlers and a custom MCAP-style path handler across obstore LocalStore, MemoryStore, and mocked S3. Cover native suffix preservation, containment, single-regular-file enforcement, round trips, create-if-absent collision behavior, exact lost-response recovery, exact immutable-generation deletion, ETag evidence, upload-bound rejection, and streaming read snapshots.
- **D-14:** Phase 07.1 must demonstrate that the custom filesystem, memory, and S3 payload mechanics and boto3 runtime path are gone, while the payload-participant composition seam remains usable and no new lifecycle authority, journal, lease, queue, lock hierarchy, or cleanup source of truth was introduced.
- **D-15:** Phase 8 owns real AWS qualification, supported-platform and packaging matrices, measured RSS/performance budgets, and SHA-256-versus-XXH3 benchmarks. Phase 07.1 proves structural bounds and deterministic behavior without duplicating those release gates.

### the agent's Discretion
- Choose the smallest internal adapter shapes that preserve the existing payload-participant protocol and handler boundary.
- Name the backend-neutral transport-evidence value and developer-facing query method, provided they remain generation-bound, optional for non-S3 stores, and explicitly noncanonical.
- Remove obsolete internal helpers after proving they have no remaining authority, migration, projection, or handler-staging responsibility.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `src/cacheness/storage/composition.py`: `PayloadGenerationIOProvider`, `RoleRegistry`, capability declarations, and topology validation already isolate payload mechanics from authority behavior.
- `src/cacheness/storage/lifecycle.py`: `AuthorityLifecycleEngine` already owns prepare, immutable publication, independent verification, promotion, replay, and exact cleanup sequencing.
- `src/cacheness/storage/guarded_handler_io.py`: private handler staging, retained-descriptor validation, suffix enforcement, contained snapshots, and regular-file checks remain required around path-based handlers.
- `src/cacheness/storage/manifest.py`: signed canonical manifest and explicit SHA-256 digest algorithm remain the payload-integrity authority.
- `src/cacheness/storage/backends/s3_backend.py`: current exact-locator validation, typed failure mapping, bounded inventory concepts, and deterministic tests are behavior to preserve while replacing boto3 mechanics.

### Established Patterns
- Authority intent is durable before any payload side effect; payload presence never establishes visibility.
- Immutable generation locators are never reused, making path-only exact deletion safe within the lifecycle contract.
- Reads materialize private suffix-preserving snapshots and verify canonical digest plus size before invoking synchronous handlers.
- Application-defined format handlers operate only on guarded local paths; no universal payload wrapper or converter is introduced.
- Capability claims come from the selected participant and qualified topology, not inferred convenience behavior.

### Integration Points
- Replace the internals materialized by `FilesystemBlobBackend`, `InMemoryBlobBackend`, and `S3BlobBackend` while keeping `PayloadGenerationIOProvider` as the lifecycle-facing seam.
- Extend publication/verification results with optional transport evidence without allowing the payload participant to mutate authority state.
- Carry signed generation-bound transport evidence through `VerificationProof`, authority persistence, promotion, `EntrySnapshot`/entry information, and the narrow developer-facing validation API.
- Preserve migration services' exact-locator and authenticated-manifest behavior; do not make obstore listing a recovery or adoption source.
- Update `pyproject.toml` and `uv.lock` only after the S3 parity gate succeeds.

</code_context>

<specifics>
## Specific Ideas

- A custom MCAP-style handler is the representative extension test because it exercises a developer-defined native file suffix without coupling the handler to obstore.
- ETag is useful as a cheap server-reported identity token persisted with the entry, but must be described as opaque evidence because multipart uploads and several encryption modes do not make it a content MD5.
- Native AWS cross-account owner pinning through `ExpectedBucketOwner` is intentionally unsupported in this cutover. Operators must use tightly scoped IAM, explicit bucket/region configuration, and stable bucket ownership; this limitation does not alter payload atomicity, catalog authority, or canonical integrity verification.
- The configured direct-upload bound is a resource constraint created by obstore's S3 API behavior, not a restriction on handler file formats or their native headers.

</specifics>
