## S3 Publication Strategy

| Option | Description | Selected |
|--------|-------------|----------|
| Direct conditional create | Use one deterministic immutable locator under a configured maximum payload size; no temporary-object lifecycle. | ✓ |
| Multipart temporary object plus conditional copy | Bound memory for larger payloads while accepting temporary objects, cleanup debt, and more recovery states. | |
| Retain custom S3 publication | Keep current boto3 multipart behavior and duplicate payload mechanics. | |

**User's choice:** Direct conditional create with a configured maximum payload size.
**Notes:** Preserve the current 128 MiB default unless planning identifies an obstore API constraint. Do not introduce multipart temporary-object cleanup coordination.

## Dependency Packaging

| Option | Description | Selected |
|--------|-------------|----------|
| Core dependency for all built-ins | Filesystem, memory, and S3 all use obstore; S3 remains explicitly configured. | ✓ |
| Optional storage/cloud extra | Base installs need separate filesystem mechanics or lose built-in persistence. | |
| Split obstore/boto3 | Use obstore locally while retaining boto3 S3 behavior. | |

**User's choice:** Make obstore a core dependency, conditional on revisiting S3 feature parity before production changes.
**Notes:** ETag retrieval is especially important. The parity gate must stop and replan if obstore lacks a capability Cacheness consumes; no quiet boto3 escape hatch.

### ETag meaning

| Option | Description | Selected |
|--------|-------------|----------|
| Opaque server evidence | Retain queryable ETag while keeping SHA-256 plus size canonical. | ✓ |
| Server full-object checksum | Require S3 checksum fields beyond ETag. | |
| Canonical ETag hash | Treat ETag as the canonical content digest. | |

**User's choice:** Preserve ETag as opaque server evidence.
**Notes:** The user values querying S3 for remote object identity without downloading and re-hashing the object.

### Canonical blob digest

| Option | Description | Selected |
|--------|-------------|----------|
| Preserve SHA-256 and benchmark | Keep the existing signed-manifest contract and measure XXH3 in Phase 8. | ✓ |
| Adopt versioned XXH3 now | Reopen Phase 5 and change manifests, authorities, migration evidence, and integrity contracts. | |
| Store both | Retain SHA-256 and add XXH3 despite added hashing/schema cost. | |

**User's choice:** Preserve SHA-256 in Phase 07.1 and file a future seed for XXH3.
**Notes:** SEED-003 was created. Phase 8 must include SHA-256-versus-XXH3 blob hashing benchmarks.

## Research Blocker Resolution

The parity spike found that obstore 0.11.1 cannot correctly sign
`ExpectedBucketOwner` across every consumed S3 operation, especially bounded
listing. Four resolutions were considered after research:

| Option | Description | Selected |
|--------|-------------|----------|
| Wait for upstream | Pause Phase 07.1 until obstore adds complete owner binding. | |
| Maintain a fork | Carry an obstore/object_store fork with owner-binding support. | |
| Revise the requirement | Drop Cacheness `ExpectedBucketOwner` support while retaining IAM, explicit bucket/region configuration, canonical SHA-256, and signed transport evidence. | ✓ |
| Abort obstore | Retain the existing custom payload implementations. | |

**User's choice:** Revise the S3 parity requirement and proceed with obstore.

**Notes:** This explicitly supersedes the Phase 5 coverage row for `Region plus
ExpectedBucketOwner`. The accepted limitation concerns defense against
cross-account bucket confusion, not payload atomicity, metadata-plus-payload
atomicity, or ADR 0001's lifecycle authority. No fork, custom signer, boto3
fallback, or parallel payload participant may be added to compensate.
