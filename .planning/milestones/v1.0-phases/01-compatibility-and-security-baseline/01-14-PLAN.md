<interfaces>
- `MetadataBackend.get_entry`, `put_entry`, `list_entries`, and `clear_all` are callbacks, not proof that a backend shares a crash boundary with the local payload root.
- Exact supported metadata identities are `json:<resolved metadata_file path>` and `sqlite:<resolved db_file path>`; the journal also binds the resolved payload-root path and its anchored `st_dev`/`st_ino`.
- `InMemoryBackend` receives a private per-instance nonce for in-process rollback. A new instance after process loss has no durable metadata and therefore rolls any stale prepared/committed journal forward to complete payload erasure; it never reconstructs ephemeral metadata from disk.
- PostgreSQL and arbitrary/custom MetadataBackend instances are unsupported by this local clear journal and must raise `CacheStorageError` with operation/backend context before a journal or tombstone is created.
- One fixed internal journal locator under the managed root means at most one unresolved clear transaction exists across callers using that root.
- Admission is keyed by resolved payload root: a shared in-process lock and, where reliable, an OS advisory lock on one fixed internal lock file are held across startup recovery and the complete clear operation. Contention is typed and non-mutating; initial journal creation is exclusive and cannot overwrite existing evidence.
- If reliable advisory locking is unavailable, startup recovery and clear fail before mutation. Multi-process clear support remains incomplete for Phase 3 rather than being silently downgraded.
- Coordinator snapshots contain both entries and hit/miss/stat counters. JSON restore must be durably acknowledged; SQLite and memory restore must be transactional. A backend adapter that cannot restore the complete state exactly is rejected before staging.
</interfaces>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Journal bytes to recovery actions | Persisted storage-controlled JSON must be bounded and fully validated before callbacks. |
| Local payload root to metadata authority | Recovery is valid only when the journal names the exact supported metadata store and anchored payload root. |
| Metadata acknowledgement to filesystem state | A clear crosses independently durable metadata and payload operations. |
| Process-local memory to restart | In-memory metadata cannot truthfully be reconstructed as durable state after process loss. |
| Same resolved root across callers/processes | Recovery and clear must have one admitted owner before any journal or payload mutation. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-01-42 | Denial of Service | Journal parser | high | mitigate | 64 MiB/100,000-entry/8,192-byte field bounds and exact cardinality before JSON-driven mutation. |
| T-01-43 | Repudiation / Tampering | JsonBackend persistence | high | mitigate | Same-directory recoverable backup, staged file fsync, replace, directory fsync, durable rollback or typed uncertain-outcome recovery, and propagated failures. |
| T-01-44 | Spoofing / Tampering | Recovery topology | critical | mitigate | Bind fixed journal to exact JSON/SQLite path and anchored payload root; reject remote/custom topology before staging. |
| T-01-45 | Tampering / Information Disclosure / Denial of Service | Interrupted or concurrent BlobStore clear | critical | mitigate | Resolved-root in-process/advisory admission, exclusive journal creation, ordered prepared/tombstone/original/metadata/committed/final-delete barriers, and deterministic reopen. |
